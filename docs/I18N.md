# Multilingual architecture

How the Playtronica Help Center becomes multilingual, and how an edit to the English source propagates to every other language.

**Source language:** English (`en`).
**Target languages:** German (`de`), Spanish (`es`), French (`fr`), Japanese (`ja`).

The English text is deliberately written to translate cleanly — see `docs/VOICE.md` (no idioms, no contractions in warnings, short declarative sentences). That voice specification is what makes high-quality machine translation possible. Do not relax it.

---

## The core principle

**English is the single source of truth. Every other language is generated, never hand-authored.**

A human edits only `content/en/`. Translations in `content/de/`, `content/es/`, `content/fr/`, `content/ja/` are produced by Claude from the English source. A translated file is never edited directly — if it is wrong, fix the English (or fix the translation prompt) and regenerate.

This keeps the model simple: one source, N derived copies, a mechanical way to know which copies are stale.

---

## The mirror tree

```
content/
  en/                       ← source of truth — humans edit ONLY this
    devices/biotron.md
    troubleshooting/hub.md
    ...
  de/                       ← generated mirror, identical tree
    devices/biotron.md
    troubleshooting/hub.md
    ...
  es/   fr/   ja/            ← same
```

Every target-language tree is an exact structural mirror of `content/en/`. Same folders, same filenames. Only the prose and the frontmatter string values differ.

## Staleness tracking — `source_sha`

Every translated file carries three extra frontmatter fields:

```yaml
---
title: "Biotron — Ihre Pflanze als MIDI-Instrument"   # translated
slug: biotron                                          # NEVER translated — URL stays stable
section: devices                                       # NEVER translated
summary: "..."                                         # translated
order: 3                                               # copied as-is
status: edited-2026-05                                 # copied as-is
emoji: 🌿                                              # copied as-is
# ─── i18n metadata ───
translated_from: en
source_sha: 3f9a1c7e            # sha256 (first 8 hex) of the EN file's body at translation time
translated_at: 2026-05-21
mt: true                        # machine-translated — not yet human-reviewed
---
```

`slug` and `section` are **never** translated. The URL path stays identical across languages, only prefixed by the language code. This keeps cross-references, redirects, and the sitemap simple.

`source_sha` is the hash of the English file's body (content after the frontmatter) at the moment of translation. When the English file changes, its hash changes, the translated file's stored `source_sha` no longer matches — and the staleness checker flags it.

Run the checker any time:

```bash
npm run i18n:status
```

It prints, per language: pages translated, pages missing, pages stale (English changed since translation). Exit code is non-zero if anything is missing or stale — so it can gate a release.

## Workflow now — manual, through Cowork (phase 1)

This is the workflow until translation volume justifies automation.

1. Edit one or more English pages — in the GitHub web editor, or locally, or by asking Claude in Cowork.
2. Commit the English change.
3. In Cowork, say: **"translate the stale pages."** Claude then:
   - runs `npm run i18n:status` to get the exact list of stale and missing pages,
   - for each, reads the English source and the existing translation (if any),
   - translates using the rules in the "Translation prompt" section below,
   - writes the target-language file with a fresh `source_sha`, `translated_at`, and `mt: true`,
   - commits.
4. Cloudflare Pages rebuilds. All languages are live.

No API key, no extra infrastructure. The cost is that Claude must be in the loop for each batch.

## Workflow — GitHub Action, automatic (built)

`scripts/translate-pages.mjs` + `.github/workflows/translate.yml` are in the repo.

**One-time setup:** add a repository secret `ANTHROPIC_API_KEY`
(Settings → Secrets and variables → Actions → New repository secret).

**Initial bulk run:** Actions tab → Translate → Run workflow. It translates every
missing page into all four languages and opens a pull request. Review the diff,
merge. This is how the first ~167 pages get translated.

**Ongoing:** the Action also runs automatically on every push to `main` that
touches `content/en/**`. It re-translates only the pages whose English source
changed (detected by `source_sha`) and opens a small pull request. The maintainer
glances at the diff and merges — translations are never silently force-pushed.

**Run it locally instead** (no Action): set `ANTHROPIC_API_KEY` in your
environment and run `npm run translate` (all pending) or
`npm run translate -- --lang de` (one language).

Model: `claude-sonnet-4-6` by default; override with the `TRANSLATE_MODEL` env
var. Cost is roughly 2–5 cents per page; the full ~167-page initial run is a few
dollars.

## Translation prompt — the rules Claude follows

When translating a page, Claude must:

- Translate **only** the prose and the frontmatter values `title` and `summary`.
- **Never** translate `slug`, `section`, `order`, `status`, `emoji`, or any URL inside a link.
- **Never** translate text inside code blocks, inline code, or `{{ youtube: ... }}` shortcodes.
- Keep every Markdown structure identical: same headings, same list nesting, same tables, same `<details>` blocks, same callout markers (`> ⚠️`, `> ℹ️`, `> 🤝`).
- Keep every link target identical. Internal links stay as `/section/slug/` — the language prefix is added by the router, not by the link text.
- Preserve the voice spec **in the target language**: short declarative sentences, no idioms, no contractions in warnings, imperative mood for instructions.
- Keep product names untranslated: TouchMe, Playtron, Biotron, Orbita, Scales, Playtronica, MIDI, USB-C, Brave, Chrome.
- Keep technical terms a local musician would expect (DAW, synth, etc.) in the form used by that language's music community.
- Set `mt: true` and a fresh `source_sha` + `translated_at`.

The full per-language glossary lives in the "Glossary" section below. Extend it whenever a term is translated inconsistently.

## Routing — built and live

The multilingual routing is **implemented**. The site renders every page in all five languages; untranslated pages fall back to English content so nothing ever 404s.

**URL scheme:** English at the root, other languages prefixed.

```
/devices/biotron/            → English
/de/devices/biotron/         → German
/es/devices/biotron/         → Spanish
/fr/devices/biotron/         → French
/ja/devices/biotron/         → Japanese
```

**How it is wired:**

- `lib/i18n.ts` — language registry, `localizedPath`, `langFromPath`, `canonicalPath`.
- `lib/content.ts` — `getPage`/`getAllPages`/`groupedNav` take a `lang`; non-English reads `content/<lang>/` and falls back to English per file. Internal links inside translated article HTML are rewritten with the language prefix.
- `components/views/` — `HomeView`, `SectionView`, `ArticleView`, `HubView` take a `lang` prop and hold all page rendering.
- `app/page.tsx` etc. (English, root) and `app/{de,es,fr,ja}/...` (16 thin route files) are wrappers that call the views with the right language.
- `components/Sidebar.tsx` + `MobileNavDrawer.tsx` receive the nav tree for every language and pick by URL prefix; `LanguageSwitcher.tsx` is in the header; `BrandLink.tsx` and `MobileBottomNav.tsx` localise their links.
- `lib/page-meta.ts` emits `hreflang` alternates + canonical + OpenGraph for every page.
- `scripts/build-seo-files.mjs` emits a multilingual `sitemap.xml` with `xhtml:link` alternates.
- `<html lang>` is corrected on the client by `components/HtmlLang.tsx`.

**Known limitation:** the troubleshooting-walker decision tree (`content/_data/troubleshooting-tree.json`) and the dev-mode search index are English-only for now. The walker's surrounding page text translates; the tree options stay English until the tree JSON is localised. Pagefind indexes all built HTML in production, so production search covers translated pages.

**Implementation steps:**

1. `lib/content.ts` — add a `lang` parameter to `getPage`, `getAllPages`, `groupedNav`. Default `en`. Each reads from `content/<lang>/`. Where a translation is missing, fall back to the English page so the site never 404s on a partial translation.
2. Add `app/[lang]/[section]/[slug]/page.tsx`, `app/[lang]/[section]/page.tsx`, `app/[lang]/page.tsx` — mirrors of the English routes, with `generateStaticParams` iterating `{de,es,fr,ja} × sections × slugs`. The English routes at the root are left untouched.
3. Guard the `[lang]` segment: `generateStaticParams` returns only the four real language codes, so `/devices/...` (English) can never be captured as `[lang]=devices`. Verify there is no collision with the root `app/[section]/page.tsx` — if Next.js complains, make the language routes a route group or an explicit allowlist check in the page component.
4. Add a `LanguageSwitcher` component in the header — a small dropdown, current language highlighted, links to the same page in each language.
5. Add `<link rel="alternate" hreflang="...">` tags for every language of a page, plus `hreflang="x-default"` pointing at English. This is the SEO signal that tells Google the pages are translations of each other.
6. `scripts/build-seo-files.mjs` — emit one `sitemap.xml` covering all languages, and a per-language section in `llms.txt`.
7. `<html lang="...">` in the layout must reflect the current language.
8. Cloudflare `public/_redirects` — optional: redirect `/de` → `/de/` and detect `Accept-Language` for first visits (Cloudflare Pages supports this via `_redirects` country/language rules, or leave it and let users pick).

**Build cost:** static export generates `pages × (1 + number of languages)` HTML files. With 42 pages and 4 target languages that is ~210 files — still trivial for Cloudflare Pages.

---

## SEO for multilingual

- `hreflang` tags on every page (step 5 above) — non-negotiable, this is how search engines avoid treating translations as duplicate content.
- One sitemap covering all language URLs.
- `llms.txt` gets a section per language so AI crawlers can find non-English content.
- Each translated page keeps its own `<meta name="description">` from the translated `summary`.
- The canonical URL of a translated page is itself, not the English page.

## What is NOT translated, ever

- `slug`, `section`, `order`, `status`, `emoji` frontmatter fields.
- URLs and link targets.
- Code blocks, inline code, file paths, `{{ youtube: }}` shortcodes.
- Product names and the company name.
- The `docs/` folder — these are maintainer/contributor docs, English only.
- `README.md`, `CONTRIBUTING.md`, and the other root files — English only.

---

## Definition of done for a translation batch

1. `npm run i18n:status` reports zero missing and zero stale pages for the languages in scope.
2. `npm run audit` still passes (translations did not break any internal link).
3. The build succeeds with the translated files present.
